$ans-governed-construction

这是一个全新的软件项目。

我要开发一个面向多 Agent 软件开发的 Agent Organization Runtime / Command Center。

这个软件的目标不是简单“同时运行多个 Agent”，而是建立一套：

**让一个人通过组织、角色、权限、任务关系、交接协议和自动治理流程，可靠管理大量自治 Agent 的系统。**

系统核心理念：

> Knowledge may be global; mutation authority must be local.

同时：

> Organizational authority must itself be bounded.

以及：

> Maximum autonomy within bounded authority.

概率模型负责规划，确定性系统负责授权。

---

# 1. 核心原则

1. 每个 Agent 必须绑定明确的 Role。
2. Role 定义职责，但 Role 描述本身不能授予实际权限。
3. 实际 Mutation Authority 必须由确定性的 Policy Kernel 强制执行。
4. Agent 只能提出 ActionProposal，不能直接绕过 Kernel 修改受保护资源。
5. Agent 在自己的合法权限范围内拥有尽可能大的自主性。
6. 权限不足不能因为“完成任务需要”而自动扩大。
7. 跨角色操作必须通过 Handoff、Delegate、Scope Expansion 或 Escalation。
8. 所有重要 Mutation 必须记录 Event。
9. 所有组织变化必须产生 OrganizationVersion。
10. 所有治理信息必须具有稳定、人类可读、机器可解析的位置。
11. 不允许把重要组织状态散落在 Prompt、聊天记录或 Agent 私有记忆中。
12. 文件系统本身必须构成系统的一个稳定 Control Plane Interface。

# 2. Client / Human / Project Owner

Client 是合法的 Mission 和 Organization Intent 来源。

Client 可以提出：

- 新 Mission；
- 创建角色；
- 删除角色；
- 修改角色职责；
- 修改角色边界；
- 拆分角色；
- 合并角色；
- 增加专业团队；
- 修改 Delegation；
- 修改 Handoff 关系；
- 调整组织结构。

例如：

- “增加一个安全审查角色。”
- “增加一个专门负责数据库的 Agent。”
- “Backend 职责太大，把数据库职责拆出去。”
- “Tester 不允许修改生产代码。”
- “给这个项目增加一个发布管理员。”

Client 的自然语言请求首先转换成：

`OrganizationRequest`

Client 提出的是：

**Organization Intent**

而不是直接改变 Organization State。

# 3. Project Manager

每创建一个 Project，系统必须自动创建：

`ProjectManager`

Project Manager 是项目组织生命周期的治理角色。

它不是万能 Agent，也不是 Root。

Project Manager 主要负责：

**Organization Lifecycle Pipeline**

包括：

- Role 创建；
- Role 删除；
- Role 修改；
- Role Split；
- Role Merge；
- Boundary 设计；
- Capability 管理；
- Reporting Line；
- Delegation；
- Handoff topology；
- Contract 管理；
- Organization Version；
- Organization Health Monitoring。

Project Manager 不一定是组织请求发起者。

请求可以来自：

- Client；
- Supervisor；
- Existing Role；
- Runtime Metrics；
- Project Manager 本身。

Project Manager 的职责是：

**接收 → 分析 → 设计 → 风险检查 → 推进审批 → 落地 → 接入 → 观察 → 演化。**

---

# 4. Project Manager 权限边界

Project Manager 拥有：

`Organization Proposal Authority`

但不天然拥有：

`Organization Approval Authority`

更不天然拥有：

`Business Mutation Authority`

因此 Project Manager 不能：

- 自己提出角色并直接使其生效；
- 自己批准自己的 Boundary Expansion；
- 给自己扩权；
- 修改任意业务代码；
- 因为缺少某角色就自己代替该角色执行；
- 绕过 Governance Gate；
- 修改 Policy Kernel 规则；
- 成为隐式 Root。

高风险 Organization Mutation 默认需要：

`Human / Project Owner Approval`

---

# 5. Supervisor

Supervisor 负责：

**Mission Lifecycle / Work Coordination**

包括：

- Mission 理解；
- Task 拆解；
- Task Routing；
- Dependency Planning；
- Handoff；
- Delegation；
- Replanning；
- 工作状态汇总；
- Capability Gap Detection；
- 任务终止判断。

但是：

**Supervisor 不是 Root。**

Supervisor 不天然拥有其他 Role 的权限。

Supervisor 可以：

`request role`

但不能：

`create role`

Supervisor 可以：

`request boundary change`

但不能：

`grant boundary change`

Supervisor 可以协调 Backend。

但不能因此直接修改 Backend 的资源。

---

# 6. Project Manager 与 Supervisor 的职责分离

必须明确：

```text
Project Manager
负责 Organization Lifecycle

Supervisor
负责 Mission Lifecycle
```

Project Manager 回答：

```text
谁应该存在？
谁负责什么？
谁拥有什么权限？
角色之间是什么关系？
组织结构是否合理？
```

Supervisor 回答：

```text
当前 Mission 怎么完成？
任务应该交给谁？
任务之间是什么依赖？
什么时候执行？
失败后怎么重新规划？
```

禁止把两者融合成一个拥有无限权限的超级 Agent。

# 7. Organization Request 来源

以下主体都可以提出 OrganizationRequest：

## Client

直接提出组织需求。

## Supervisor

发现 Capability Gap。

## Existing Role

发现当前职责无法覆盖任务，并且不存在合法 Handoff Target。

## Project Manager

根据组织运行情况主动提出优化建议。

## Runtime Metrics

根据运行数据生成 OrganizationSignal。

例如：

- ScopeExpansionRequest 过多；
- Handoff 过多；
- 某 Role 长期成为瓶颈；
- 某 Role 长期空闲；
- Write Scope 冲突频繁；
- 某类任务没有责任主体；
- 某角色重复返工。

Runtime 只能产生 Signal。

不能直接改变 Organization。

# 9. Role Creation 原则

不能因为用户说：

“创建一个 Database Agent”

就立即启动一个数据库 Agent。

首先产生：

`RoleCreationRequest`

然后分析：

- 是否真的需要长期 Role；
- 当前是否已有类似 Role；
- 是否应该修改已有 Role；
- 是否只是一次临时 Task；
- 是否存在职责重叠；
- 是否存在 Write Scope 冲突；
- 是否需要修改已有角色 Boundary；
- 是否需要新增 Contract。

然后形成：

`CandidateRoleDefinition`

Candidate Role 不具有实际权限。

但是：

**你是谁，你负责什么。**

`boundary.yaml` 表示：

**你真正被允许做什么。**

Role 描述不能覆盖 Boundary。

# 11. Work Mutation 与 Organization Mutation

系统必须明确区分两种变化。

## Work Mutation

例如：

- 修改代码；
- 修改测试；
- 修改文档；
- 修改配置；
- 数据库 schema；
- shell command；
- Git commit；
- 业务状态变化。

由：

`Role Policy`

控制。

---

## Organization Mutation

例如：

- CreateRole；
- DeleteRole；
- ModifyRole；
- SplitRole；
- MergeRole；
- ChangeBoundary；
- GrantCapability；
- RevokeCapability；
- ChangeDelegation；
- ChangeReportingLine；
- ChangeContract；
- ChangeOrganizationTopology。

由：

`Organization Governance`

控制。

二者必须使用不同 Proposal 和 Commit Pipeline。

# 12. ActionProposal

Agent 不直接执行受保护 Mutation。

Agent 首先提交：

`ActionProposal`

Kernel 必须检查：

- Active Role；
- Target Resource；
- read/write scope；
- deny scope；
- capability；
- tool permission；
- current state；
- required approval；
- delegation context；
- task ownership；
- organization version。

返回：

```text
ALLOW
DENY
REQUIRE_APPROVAL
REQUIRE_HANDOFF
REQUIRE_SCOPE_EXPANSION
```

只有 ALLOW 后才允许执行真正 Mutation。

---

# 13. 关键安全规则

必须禁止：

1. Agent 自己扩大自己的权限；
2. Supervisor 给自己增加业务权限；
3. Project Manager 给自己扩权；
4. Project Manager 自批组织变化；
5. 角色缺失时其他 Agent 自动顶替；
6. Agent 因任务需要自动获得权限；
7. LLM 自己决定权限结果；
8. Tool 间接绕过 Policy；
9. Delegation 洗权限；
10. Handoff 洗权限；
11. Role Creation 自动继承创建者权限；
12. 新角色默认拥有全局 Write；
13. 高权限角色成为隐式 Root。

原则：

> Responsibility gap must not become an authorization bypass.

# 21. Contract 与 Handoff 必须分开

Contract 表示长期稳定接口。

```text

```

Contract 存：

```text
.ans/contracts/
```

Handoff 存：

```text
.ans/handoffs/
```

禁止混淆。

**合法任务依赖与状态转换空间。**
