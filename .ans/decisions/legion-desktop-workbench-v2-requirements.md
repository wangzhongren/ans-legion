# 桌面工作台修订：客户反馈

日期：2026-10-07。记录角色：ANS Governance。

客户在查看实际发行包角色页后指出：“你没有一个聊天界面，我怎么把我的需求发给对方呢”，随后指出：“还有界面太丑了，一点都不专业啊。”这构成当前桌面交付目标的修订：必须有实际需求对话入口，并重做工作台视觉和信息层次。

原 GUI v1 的授权、冻结方案、六个已核验节点及独立审查中的真实失败仍保留，不把该观察面板标为客户满意交付。当前 revision36 全部 inactive，Reviewer 8/8 通过，Tester 未派发。新工作台行为尚未实现，也未取得新方案的实施确认。Supervisor 组织固定 ProjectManager 及受影响 owner 进行只读方案评估。

客户曾提出默认接待创建 ProjectManager，随后最终纠正：“实际上我更希望是一个，就是项目管理。”最终要求覆盖之前的两角色建议：唯一 Human 聊天入口是项目管理，选择文件夹后的首条消息自动创建或绑定此项目的管理会话；讨论、确认、结果汇报在同一会话中。其他动态 Agent 只能由项目管理创建与调度，用户只能看任务和状态，无法直接聊天或启动。开发 Legion 自身的固定七角色，不等同于用户项目的组织。没有收到需求即自动执行的授权。

新方案必须覆盖真实项目管理对话、可确认的任务计划与真实 Agent 执行。初始对话与计划阶段不授予项目文件写权限，也不产生客户目录审计文件；确认具体计划后按任务绑定名称、连接版本、roleId、组织版本、上下文快照与精确 writeSet。已有许可内核、取消与审计行为仍需复用并验证。

视觉目标：桌面开发工作台，中心为对话与任务、左侧项目和角色、右侧可收起详情；AI 配置移到设置。减少巨大标题、宽松卡片和重复提示，统一字号、间距、状态与操作反馈。保留明确的真实状态、文件范围和错误信息，以按需展开的详情表达。

独立 Reviewer 实际确认当前 GUI 自身任务记录也已超过原 1MB 预算，新方案须使本项目当前任务可读取，并保持有限资源预算与来源验证。旧超限记录不等同业务失败。

下一步是形成具体修订方案和管理评审，再确定精确实施范围。Root 仍为 ANS Governance，不写应用、测试或打包源码，不把前版 ZIP 作为修订版成品。
